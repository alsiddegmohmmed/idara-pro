# ADR-0005: Store uploaded files on local disk behind a storage interface

**Status:** Accepted
**Date:** 2026-09-26
**Deciders:** Siddeg
**Supersedes:** the "Files: MinIO" line of ADR-0002

## Context
Idara Pro stores uploaded files: employee documents (Iqama, passport, contracts),
payslip PDFs and Techno Link export files. ADR-0002 chose MinIO (self-hosted,
S3-compatible). In 2026 MinIO stopped distributing its community edition: the
Docker Hub images were removed (Sept 2026) and the quay.io image is frozen,
unpatched and refuses anonymous pulls. It can no longer be installed reliably.

Constraints: one company, one self-hosted server, a modest number of files
(thousands, not millions), one developer, files must be in the backups.

## Decision
- Store files on the server's disk, in a Docker volume (`idara_files`) mounted
  into the `api` container at `/var/lib/idara/files`. Local dev uses
  `apps/api/storage/` (gitignored).
- All code uses a `FileStorage` port (in `apps/api/src/shared/storage/`):
  `put(key, stream, contentType)`, `get(key)`, `delete(key)`, `exists(key)`.
  v1 has one adapter: `LocalDiskStorage`. The storage directory comes from a
  `FILE_STORAGE_DIR` env var, added when the first module needs files (Phase 1).
- The database stores only the file key + metadata (name, type, size, checksum),
  never the file bytes.
- Keys are generated by the server (`<companyId>/<entity>/<uuid>`), never from the
  user's file name, to prevent path traversal.
- Downloads go through the API (permission check + audit), never a public URL.
- Backups copy the volume together with the nightly `pg_dump`.

## Options considered
| Option | Complexity | Ops on own server | Maintenance risk | Fit |
|---|---|---|---|---|
| **Local disk + interface** | Lowest | None extra | None | Best for 1 server |
| SeaweedFS / Garage (S3-compatible) | Medium | +1 service to run and patch | Low–medium | Good if files grow a lot or several servers |
| MinIO (quay.io frozen image) | Medium | +1 service | High: unpatched, pull failures | Rejected |
| Files in PostgreSQL (bytea) | Low | None | Bloats DB and backups | Rejected |

## Consequences
- Easier: one less service; nothing to download or patch; backups are one folder.
- Harder: the API must stay on one server (or share the volume) while files are local.
- Revisit when: a second API server is added, or storage grows past what one disk
  and its backup can handle. Then add an S3 adapter (e.g. SeaweedFS) implementing
  the same `FileStorage` port and migrate the files; no module code changes.
